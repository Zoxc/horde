# Lean model of `src/collect.rs`

Build: `cd lean/collect && lake build` (Lean core only, no Mathlib; builds in a few seconds). `lean/sync_table` depends on this package (lake path dependency `../collect`) and uses `Collect.Main.safety` and the primary model `Collect.Ev`.

Files:
- `Collect/Model.lean`: state, operations, `Step` relation, `Reachable`, ghost `blocked`.
- `Collect/Count.lean`: the `busy_count`/`threads.len()` invariant `CInv` and its preservation by the collector operations.
- `Collect/Safety.lean`: inductive invariant `Inv` and the main safety theorem.
- `Collect/Progress.lean`: cancellation, small progress lemmas and the weak liveness theorem `eventually_ran`.
- `Collect/Live.lean`: `Ev.eventually_ran_keep`, the flag-keeping (`cancel_by_ids`-free) form of `eventually_ran_events`.
- `Collect/Events.lean`: **the primary model** `Ev.EStep`/`Ev.EReach`: the base model plus `EVENTS`/`seen_events` (namespace `Collect.Ev`), the refinement proof, the fast-path theorems and the wrap-around counterexample.
- `Collect/Main.lean`: the headline theorems restated on the primary model (namespace `Collect.Main`).
- `Collect/Fair.lean`: fair (infinite-trace) liveness on the base model, see "Fair liveness" below.
- `Collect/EFair.lean`: fair liveness on the primary model `Ev.EStep` (namespace `Collect.EFair`), with fairness on `collect` calls that may take the fast path, and the wrap-around counterexample. See "Fair liveness", variant 3.
- `Collect/Flags.lean`: `defer_by_id` flag memory (`Flags.FSt`: `Cell` = `unalloc`/`live`/`freed`, the flag values `val`, ghost allocation time `born`), the client obligation as premises of `Flags.FStep.deferId`/`free`, no write-after-free / `debug_assert!` results, and the flag-value results (property 13).
- `Collect/EFlags.lean`: property 13 on the primary model (namespace `Collect.EFlags`): `EFSt` (`Ev.ESt` plus the flag heap/values/`born`), `EFStep` (`Ev.EStep` with the flag effects and client-obligation premises of `Flags.FStep`; stutters store nothing), `EFReach`, the projection `efreach_freach` onto `Flags.FReach`, and the property-13 theorems restated.
- `Collect/Weak.lean`: the `Pin` contract in lock-order (happens-before) terms instead of SC ghost time (namespace `Collect.Weak`), see property 11.
- `Collect/RC11.lean`: a generic RC11-style weak-memory layer (namespace `RC11`, no `collect` content): events with modes `na/rlx/acq/rel/acqrel/sc`, execution graphs (`po`, `rf`, `mo`), `fr`, `eco`, C++20 release sequences, `sw` (with fences), `hb`, RC11 consistency (coherence, atomicity, no-thin-air; no SC axiom since the crate uses no `SeqCst` outside tests), mutexes as lock locations (`LockLoc`, `lock_mo_hb`: lock order `⊆ hb`), message passing (`mp_hb`, `hb_read_coh`), and linearisations of finite graphs (`exists_hb_lin`, `lin_po`, `lin_lock_hb`). Also used by `lean/sync_table` (`SyncTable/RC11Publish.lean`, and `SyncTable/RC11Table.lean` for its property 18: writer operations under a lock location, per-`get` placement of reader loads).
- `Collect/RC11Live.lean`: fair liveness under weak memory (namespace `Collect.RC11Live`): the weak model `LStep` (the primary model with stale `EVENTS` loads outside the lock, per-thread views `vw`), the eventual-visibility axiom `EvVis`, the fair liveness theorems `lfair_stable`/`lfair`, `lfair_needs_vis`, weak liveness `lreclaim_possible` (from every weak-model state), and RC11 read-read coherence `corr`. See "Fair liveness", variant 5.
- `Collect/RC11LiveGraph.lean`: the weak model derived from RC11 execution graphs (namespace `Collect.RC11LiveGraph`): executions as a consistent graph plus an enumeration of its events along `(po ∪ rf)⁺` (`Enum`; `RC11.Graph.porf`, `hb_porf`, `exists_lin_porf`), the interface `LGraph`, the replay `LGraph.replay`/`run`/`lab` as an `LExec` run (`lexec`), the load rule (`load_rule`), the index and values of `EVENTS` writes (`idx`, `idx_lt`, `idx_bump`, `wval_idx`), in-lock loads (`RC11.Graph.inlock_exact`), eventual visibility on graphs (`GEvVis`, `evvis_run`), and fair liveness over graphs (`gfair_stable`, `gfair`). See "Fair liveness", variant 5.
- `Collect/RC11Pin.lean`: property 11 over RC11 execution graphs (namespace `Collect.RC11Pin`): the interface `CExec` (what an execution graph of a `collect` program is), the replay of a linearisation as a `Weak.WReach` run (`replay_wreach`), and `pin_contract`/`pin_contract_run`/`pin_contract_flag`.

The base model (`Model.lean`, `Safety.lean`, `Progress.lean`) is an abstraction in which `collect_cold` may run at any time. Every primary step projects to a base step or a stutter (`Ev.estep_base`), which is how invariants are transferred.

## Simplifying assumptions

1. **Atomicity and memory model.** Each `Collector` method runs under the `COLLECTOR` mutex, so it is modelled as one atomic step. That is sound because the mutex gives a total order with happens-before edges. Thread-local updates are steps of their own thread, which makes them atomic trivially. The model itself is sequentially consistent; `Collect/RC11Pin.lean` justifies this for the safety property: from any RC11-consistent execution graph satisfying the interface `CExec`/`Valid`, replaying a linearisation of `hb` gives a model run, and the `Pin` contract follows in `hb` terms (property 11), including the `Release` store in `mark_ready` and the client's `Acquire` load of the flag (`pin_contract_flag`). The program-to-graph mapping is the axiomatised part (property 11). For liveness, `Collect/RC11Live.lean` drops sequential consistency for the only non-lock atomic that matters, `EVENTS`: its three loads outside the lock (`collect`'s `Acquire` check, `collect_cold`'s and `pin_cold`'s `Relaxed` loads) may read any write `wₖ` with `vw t ≤ k ≤ total` (stale value `k % W`; `wₖ` is the `k`-th bump in lock order, which is `EVENTS`'s modification order since every bump is a `fetch_add` under the lock), and liveness is proved under the eventual-visibility axiom `EvVis` (property 10, variant 5). `Collect/RC11LiveGraph.lean` derives this rule from RC11-consistent execution graphs satisfying the interface `LGraph`/`Valid` (finite, or infinite and presented by a `(po ∪ rf)⁺`-respecting enumeration): the replay is an `LExec` run in which each out-of-lock load reads the write given by `rf`, with index `k` (its position in `mo`) satisfying `vw t ≤ k ≤ total` and value `k % W` (`load_rule`), and eventual visibility on the graph gives `EvVis` on the run (`evvis_run`). The interface axiomatises that the `EVENTS` writes are the initialisation write and lock-ordered (`hb`-ordered) `fetch_add`s, and that the program is valid along the enumeration, including that a `fetch_add` event only occurs when the replayed critical sections have charged it (`placed < total`) and, for infinite executions, that every charged `fetch_add` occurs (`BumpsDone`).
   - The locked steps that bump `EVENTS` (`EStep.defer`, `collectReg`, `collectUnreg`, `release`) are atomic only because every `EVENTS` bump in `collect.rs` happens while the `COLLECTOR` lock is held (`defer*`, `complete_epoch`). A bump outside the lock would break this.
   - The `Pin<'a>` contract ("pinned at or before the defer") is interpreted in the model's sequentially consistent ghost time (`St.now`, pin start times, `Cb.time`) by `safety`. `pin` and the end of a region do no synchronisation, so this ghost order is not a happens-before order. `Collect/Weak.lean` (property 11) proves the version that only uses the mutex's lock order, and `Collect/RC11Pin.lean` derives it from RC11-consistent execution graphs (a model trace is obtained by replaying a linearisation of `hb`; the axiomatised interface is `CExec` plus the program assumption `Valid`, see property 11).
2. **`EVENTS` step granularity.** The `Relaxed`/`Acquire` loads and `Release` bumps are sequentially consistent (see 1). Every `EVENTS` access outside the lock is its own step: `collect`'s check (`collectCheck`), `collect_cold`'s reload and store (`collectStore`), and `pin_cold`'s forced store after `register` (`pinForce`), so bumps by other threads in between are covered. Stores inside the lock (`defer*`, `complete_epoch`, `quiet`'s store before recursing) are part of the locked step, in Rust's order. Further details:
   - The `debug_assertions`-only `assert_collect_state` in `collect` is folded into `collectCheck`/`collectFast` being enabled only in `Registered`/`Unregistered` (in release builds a `collect` from other states with no news is a no-op, which is a stutter).
   - In `pinRegister` the thread is marked `Pinned` already at the locked `register`. Its local state writes are invisible to other threads, and being pinned earlier only makes `safety` stronger.
   - Every thread starts with `seen = 0, gseen = 0`. A thread whose `Data` is created late in Rust also starts at `seen_events = 0`, so this matches: it can miss events if `EVENTS` is then a multiple of `W`.
   - **Overflow caveat:** `collect` misses events exactly when the number of bumps since `seen_events` was stored is a positive multiple of `W` (`fast_path_misses_iff`, `defer_W_misses`). Reclamation is then delayed until the next bump. On 64-bit this needs 2^64 bumps between two `collect` calls of one thread.
3. **Panics are not modelled.** Panics from misuse (`pin`/`collect`/`release` in invalid states) are modelled as the step not being enabled, because the Rust code checks these before mutating anything. Callback panics are caught, and the remaining callbacks still run, so the model's run-to-completion covers the collector-visible effect. A panicking `pin` closure restores state through the guard, which matches `unpin*`. Aborts (exiting while pinned or collecting, a payload destructor panicking) are out of scope.
4. **Callbacks deferring from inside callbacks** is covered, because `Step.defer` is enabled in every thread state. Callbacks calling `pin`/`collect`/`release` panic in Rust, and the model disables those steps for `collecting`.
5. **`defer` is an environment action.** `Step.defer`/`EStep.defer` take no thread argument and are always enabled, so a `defer` is not attributed to any thread or thread state. This over-approximates Rust (more behaviours, so safety results are stronger). For the weak liveness results (8, 8b, 8c) it means the witness schedule may itself add a `defer` (8b/8c, to escape a wrap-around miss) and may make every thread `release`; these schedules exist in the model, not necessarily in a given program.
6. **Windows process exit** (`process_is_exiting`), TLS teardown order (`EXIT_GUARD.try_with`), `hide`, `cold_path`/`unlikely`, `LazyLock` and `HashSet`/`HashMap` details are ignored. `threads.is_empty()` is `allNone threads` (equivalent to `len = 0` by `len_zero_iff`).
7. Thread exit through `ExitGuard` is `release`. A thread that dies without running destructors is simply a thread that takes no further steps.
8. **Fair liveness.** `Fair.lean` works with the base `Step` (where `collect_cold` may run at any time), with fairness on *slow-path* collects (`CollectsAt`). `EFair.lean` proves the results on the primary model `Ev.EStep`, with fairness on `collect` calls (fast path included), but only under a no-wrap-around hypothesis (`EFair.NoWrapAt`/`NoWrapAny`, or the event bound of `EFair.efair_bounded`). That hypothesis is necessary (`EFair.wrap_starves`). `RC11Live.lean` proves them for the weak model with stale `EVENTS` loads, under the eventual-visibility axiom `EvVis` (necessary: `lfair_needs_vis`) and no wrap-around relative to the value read (`NoWrapL`).
9. **`defer_by_id` client obligation.** `Flags.FStep.deferId`/`free` take the client obligation as premises. `assert_never_fires` restates that obligation (its premise is the negation of `assertFires`, `assertFires_iff`); it is equivalent to Rust's `debug_assert!`s not firing only under sequential consistency (1). The `Release` store and the client's `Acquire` load on the flag are covered only by sequential consistency (property 11); a client's reset of a flag to `false` without reallocating it is not a step (no client does this).

### Modelled exactly

- `EVENTS`/`seen_events`: modelled exactly by the primary model `Ev.EStep` (any width `W`, every bump site, all three `seen_events` stores, `pin_cold`'s forced value); the base model is an abstraction of it (`estep_base`, `ereach_base`). `quiet`'s bump count and recursion match Rust (`qBump_rust`, `qInner_rust`, `qRecurses_rust`, `qInner_current`).
- `quiet` recursion: `Step` uses the literal `quietRust` (well-founded recursion); it recurses at most once, for every state (`quietRust_cur_nil`, `quietRust_eq`: `quietRust t s = quiet t 2 s`).
- `busy_count`: an explicit counter `St.busy`, exact and never underflowing (property 9, `CInv`, `unregister_no_underflow`, `quiet_no_underflow`).
- `defer_by_id` flag memory and value: modelled in `Flags.lean` (`FSt.val`, `flag_true_iff`, `only_collect_writes_true`, property 13). Writes by other owners to memory that is not a live flag (freed, or reallocated to a non-flag owner): `FStep.envWrite`/`EFStep.envWrite`; `flag_true_iff` is stated for live flags.

## Want to fix

### 1. `EVENTS` wrap-around starves the fast path (low priority)

If other threads do exactly a multiple of `W` defers (2^64 on 64-bit) between a `Busy`
thread's `seen_events` store and its next `collect` check, that check takes the fast path
(`fast_path_misses_iff`, `defer_W_misses`). If this repeats forever, the thread never quiets
and no epoch completes (Fair liveness, variant 3; mechanised as `EFair.wrap_starves`). It needs about 2^64 bumps between two
`collect` calls of one thread, so it is only theoretical on 64-bit. It is more plausible on
32-bit (2^32 bumps). A fix would be to make `EVENTS` wider (`AtomicU64` everywhere). Another
fix would be to occasionally force the slow path, for example after a bounded number of fast
paths.
